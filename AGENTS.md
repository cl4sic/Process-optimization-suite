# Agent Guidelines: Process Optimization Suite

This document defines guidelines, design principles, and engineering standards for any AI agent or contributor working in this repository.

---

## 1. Project Overview & Problem Context

This project is a **Process Optimization Suite** dedicated to solving the **Permutation Flow Shop Scheduling Problem (PFSP)**.
- **Problem Statement:** We have $n$ jobs that must be processed on $m$ machines in the identical order ($M_0 \rightarrow M_1 \rightarrow \dots \rightarrow M_{m-1}$).
- **Constraints:** A machine can only process one job at a time; a job can only be processed on one machine at a time; no preemption.
- **Objective:** Minimize the **Makespan** ($C_{\max}$), which is the total completion time of all jobs on the final machine.
- **Implemented Heuristics:**
  1. Pure Random Search (`algoritmo_busqueda_aleatoria`)
  2. Local Search - Best Neighbor (`algoritmo_local_mejor`)
  3. Local Search - First Best Neighbor (`algoritmo_local_primer_mejor`)
  4. Simulated Annealing (`algoritmo_sa` with geometric cooling and 2-opt neighborhood)
  5. Genetic Algorithm (`algoritmo_ga` with Order Crossover OX, swap mutation, and elitism)
  6. Solution Polish (`pulir_solucion` local search post-processor)

## 3. Engineering Guidelines for AI Agents

### 3.1. Web Engine & Web Worker Rules
- **Non-blocking Execution:** Never run long optimization loops on the main UI thread. All heuristics must execute inside a dedicated **Web Worker** (`web/src/core/worker.ts`).
- **Throttled Streaming:** Emit progress updates (`postMessage`) at reasonable intervals (e.g., every 5-10 generations or 30-50ms) to ensure smooth 60fps UI rendering of the convergence curve without event buffer congestion.
- **Strict Typing:** All data models (`ProblemInstance`, `Solution`, `ScheduleBlock`, `AlgorithmResult`, `WorkerMessage`) must be strictly typed in `web/src/core/types.ts`. Avoid `any`.

### 3.2. UI & Design System Rules
- **Design Aesthetic:** "Dark Industrial / Pro Dashboard" inspired by Linear/Vercel. Use dark slate/zinc backgrounds (`bg-zinc-950`, `bg-zinc-900/60`), subtle borders (`border-zinc-800`), and vivid accents for charts and jobs.
- **Gantt Chart:** Must be rendered dynamically via SVG. Each job gets a distinct, consistent color generated by an HSL algorithm (`hsl((jobId * 137.5) % 360, 75%, 55%)`) so individual jobs are instantly traceable across all machines. Tooltips must show: Job ID, Machine ID, Start Time, End Time, Duration, and Idle Gap.
- **Responsiveness:** Support horizontal scrolling or zoom on the Gantt timeline for large problem instances (e.g., 200 jobs x 20 machines).

### 3.3. C++ Code Maintenance Rules
- Maintain standard C++17/C++20 compatibility with no external dependencies (only standard `<vector>`, `<algorithm>`, `<cmath>`, `<chrono>`, `<fstream>`, `<iostream>`).
- Always support compiling via `g++ -O3 -Wall -Wextra`.

## 4. Verification and Quality Checklist

Before submitting changes or completing a phase:
1. Verify TypeScript builds without errors: `npm --prefix web run build`.
2. Ensure the Gantt chart and convergence plots render cleanly for both small (5x2) and large (200x20) datasets.
3. Test C++ compilation: `make -C cpp`.
4. Keep `CHANGELOG.md` updated with every new feature or refactor.
